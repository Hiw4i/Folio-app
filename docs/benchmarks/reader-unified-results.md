## Честные ограничения

- Окно кадров 3 с и по одному холодному открытию — ниже минимумов полного
  протокола; это guardrail-сравнение, не приёмка производительности.
- Окно кадров измеряет смонтированный документ в статичном состоянии;
  скролл/pinch/scrub-сценарии — в расширенном harness Задачи 8.
- Мощное устройство (S25 Ultra) на момент прогона было занято; второй
  прогон на нём остаётся в плане Задачи 8.

## v2 (управляемые окна + 10 повторов, то же устройство, тот же профиль)

Harness v2: 1 fresh-process cold + 10 cache-warm повторов + 3 с settle +
**10 с управляемого окна** — свипы seek/scroll через те же API рендереров,
которые вызывают продакшн-адаптеры (растеризация PDF-страниц, прыжки
Office, прыжки текстового скролла). Обе стороны исполняют идентичный код
измерений (без binding-слоя — он отсутствует в baseline-теге).

Свипы — это намеренно максимальный темп прыжков (каждые 80 мс), а не UX-сценарий:
они вскрывают реальные hot spots (полный свип текста перестраивает 600 строк —
p95 UI ~192 мс; свип 24-страничного PDF растеризует страницы — 20 % кадров
сверх бюджета). Для вывода guardrail важно: **дельты до/после по всем
форматам в пределах шума**, худшие места одинаковы на обеих сторонах.

### Память: 20 циклов открытия/закрытия × 2 файла (docx_big_images + PDF)

Суммарный PSS процессов приложения (основной + WebView renderer), profile:

| Раунд | До (last PSS) | После (last PSS) |
| --- | --- | --- |
| 1 | 254 149 kB | 286 430 kB |
| 2 | 283 832 kB | 265 323 kB |
| Медиана раундов | 268 990 kB | 275 876 kB (**+2,4 %**) |

Разбор сигнала первого раунда (+12,7 %): контрольные прогоны показали
межпрогонный разбег ±12 % на ОБОИХ сторонах (до: 254→284, после: 286→265),
распределения перекрываются, внутри каждого прогона дрейфа за 40 циклов
нет (max−min ≤ 8 МБ). Вывод: данные уровней PSS на этом устройстве
доминируются шумом WebView/GPU-состояния, регрессии не выявлено; плотная
выборка пика и multi-process Perfetto остаются за полной кампанией Задачи 8.
